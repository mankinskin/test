## Per-Scenario Calibration for Heterogeneous Scenario Matrices

A single `group.sample_size(N)` / `group.measurement_time(D)` applied once for an entire `benchmark_group` is a blunt instrument when the group's scenarios vary enormously in per-iteration cost (e.g. a matrix over entity count and link density). One blanket budget either wastes time re-sampling cheap scenarios far past their needed precision, or forces Criterion to silently overrun (`Unable to complete N samples in D` warnings) on expensive ones — and across a 200+-scenario matrix those overruns compound into hours. See [benchmarks-timeout.instructions.md](benchmarks-timeout.instructions.md) for the outer timeout policy this section reduces the need for.

The fix, applied in `workflow-tools/ticket/crates/ticket-api/benches/move_health.rs` (`calibrate_scenario_cost`, `measurement_budget`, `bench_move_scenario_matrix`): run one real, untimed-by-Criterion setup+measure cycle per scenario with `std::time::Instant` immediately before registering it, then call `group.warm_up_time(...)` / `group.measurement_time(...)` with a budget derived from that real measurement, before the `group.bench_with_input(...)` call for that scenario. Criterion applies group config to the *next* benchmark registered, so this must happen in-loop, per scenario, in order — it is not a workaround, it is the intended way to vary Criterion's budget across a group with heterogeneous costs. `sample_size` has a hard floor of 10 (Criterion rejects lower); shrink `measurement_time`, not `sample_size`, to fit an expensive scenario's real budget.

Once calibration is in the loop, guard it behind the same filter Criterion itself uses (`cargo bench -- <substring>` matches on `group/function/parameter`). Without that guard, a single-scenario filtered run still pays the real setup cost of *every* scenario in the matrix before Criterion ever applies its own filter — the calibration step runs unconditionally ahead of Criterion's dispatch, so an unfiltered pre-check silently reintroduces the "expensive setup repeated needlessly" problem the calibration was meant to fix.

A cheap `<ENV_VAR>=1` "estimate-only" mode that runs just the one-shot calibration for every scenario in the matrix (skipping the real 10-sample Criterion collection) and sums the resulting budgets gives a real, measured total-time estimate for the whole matrix — at roughly 1/10th the cost of actually running it — before committing to the full run. Prefer this over guessing a flat per-scenario cap: real data from one matrix showed linkage cost is not negligible next to entity count — 25 entities × 5 internal links calibrated to ~12.1s/iteration versus ~3.8s at 0 links (over 3x), so a scenario matrix keyed on more than one dimension cannot have its cost derived from entity count alone; measure every dimension that varies.

Criterion's own `Warming up for X s` / `Collecting N samples in estimated Y s` console output is itself real per-iteration cost data — read it instead of discarding it via `--test` smoke mode, which produces zero timing information at all.
